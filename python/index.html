Morning — SQL Wrap-Up: Subqueries & Segmentation
🪆
01 · Core Concept
Subqueries — Queries Inside Queries
▼
Core Idea

Take raw data, create a higher-level intermediate form, then query that intermediate result. Subqueries avoid hardcoded values, making the logic reusable and portable.

Canonical Example — Cities Above the National Average

Dataset: NYU zero_transactions table — columns id, state, city, address, market_price; 10 cities including NYC, Chicago, San Francisco, Santa Clara.

  1. National average: SELECT AVG(market_price) FROM zero_transactions
  2. City-level averages: SELECT city, AVG(market_price) FROM zero_transactions GROUP BY city
  3. Filter to cities above the national average using HAVING
  4. Replace the hardcoded value with the subquery in parentheses
SELECT city, AVG(market_price)
FROM zero_transactions
GROUP BY city
HAVING AVG(market_price) > (SELECT AVG(market_price) FROM zero_transactions)

Result: San Francisco, Santa Clara, and one other city.

⚖️
02 · Key Distinction ★
WHERE vs. HAVING
▼
WHEREHAVING
When it filtersBefore aggregation — individual rowsAfter aggregation — on the aggregate result
Use caseOnly include transactions above a price before groupingOnly return cities where the computed average exceeds a threshold
AggregatesCannot filter on an aggregate valueBuilt for it
Alias Gotcha

Aliases in HAVING may work in some SQL engines but it's not guaranteed — safer to repeat the full expression (e.g. HAVING AVG(market_price) > ...).

Variables as a Readability Alternative

SET national_avg_price = (SELECT AVG(market_price) FROM zero_transactions);
-- then:
HAVING AVG(market_price) > national_avg_price

Identical semantics, significantly more readable. Preferred during development before packaging into a CTE.

03 · Patterns
Semi-Joins & Anti-Joins
▼

Semi-Join — Filter With Another Table, Return Columns From One

Example: get all drama or comedy movies. Join genre table → movies table, then SELECT DISTINCT on movies only to kill duplicates from the one-to-many join. Cleaner alternative when you don't need any columns from the second table — the subquery acts purely as a filter:

SELECT * FROM movies
WHERE movie_id IN (SELECT movie_id FROM movie_genre
                   WHERE genre IN ('drama','comedy'))

Anti-Join — Rows That Do NOT Appear in Another Table

Example: all movies not tagged as adult:

SELECT * FROM movies
WHERE movie_id NOT IN (SELECT movie_id FROM movie_genre
                       WHERE genre = 'adult')
  • Correctly handles multi-genre movies: a film tagged adult + drama is excluded entirely
  • Writing this as a regular join + filter is complex and error-prone; the subquery form is much simpler
Null Caveat

If a movie has no genre entry at all, it won't appear in the genre table and therefore won't be blocked by the anti-join — it slips through.

04 · Applied
Music Recommendation via Segmentation
▼

Semi-join logic applied to build a basic recommendation system: find the favorite music of people who like a specific artist (e.g., Coldplay). Tables: profiles (profile_id) and favorite_music (profile_id, music, likes).

  1. Base query: GROUP BY music, count likes across the full population → overall popularity
  2. Segment: add WHERE profile_id IN (SELECT profile_id FROM favorite_music WHERE music = 'Coldplay') — limits the population to Coldplay fans before computing popularity
  3. Re-segment instantly by swapping 'Coldplay' for 'Mozart' or any other artist

Results: Coldplay fans also like Radiohead, Modest Mouse, Bag Raiders, etc.

Limitation → Improvement

Raw popularity counts are biased toward globally popular music. Improvement: control for overall popularity so only music that is disproportionately popular within the segment surfaces as a recommendation.

The same pattern applies to any segment: gender, relationship status, age group, political views.

05 · Applied
Book Preferences by Political Affiliation — Lift
▼

Dataset: profiles (profile_id, political_views) + favorite_books (profile_id, book_id). 936 conservatives vs. 6,461 liberals — a significant imbalance that makes raw counts misleading.

  1. Most popular books among liberals (semi-join on political_views = 'liberal')
  2. Repeat for conservatives
  3. Normalize by group size to get percentages: liberal_pct = COUNT(profile_id) / 6461, conservative_pct = COUNT(profile_id) / 936
  4. Join the two result tables on book to compare side by side
  5. Compute lift: liberal lift = liberal_pct / conservative_pct (and vice versa). Lift > 1 = the book over-indexes for that group.
BookSkew
Kite Runner~9× more likely for a liberal to like it
Bible · 1984 · Mere Christianity · MoneyballSkew conservative
Harry PotterLiked by both groups at similar rates
Key Insight

Even with 25,000 college students from ~20 years ago, the signal is real and interpretable. Scale to billions of users and you can infer political leanings, purchase intent, and voting likelihood from book or music preferences alone.

06 · Structuring Queries
Derived Tables, CTEs & Materialized Views
▼

Derived Tables — Subquery in the FROM Clause

Example: airport competition analysis using DOT flight data (25 years, all US airports):

  1. Stage 1: GROUP BY origin airport → COUNT DISTINCT carriers and destinations
  2. Stage 2: query that result → GROUP BY carrier_count, COUNT airports — how many airports are served by exactly 1, 2, 3, 4+ carriers

Stage 2 cannot run directly on the raw table — you need the intermediate aggregation first.

Temp Tables During Development

CREATE TEMP TABLE airport_stats AS (stage 1 query);
-- then run stage 2 as a separate query on airport_stats

Best during development: you can inspect intermediate results at each step.

Materialized Views — Pre-Compute & Physically Store

  • Useful when the underlying table is large (e.g., 300M rows) and the query is expensive to rerun
  • Scheduled refresh: admin sets an interval (e.g., every 15 minutes)
  • Incremental (delta) refresh: system detects source changes and updates only affected rows — BigQuery supports both, but incremental isn't supported for all query types
  • Trade-off: faster reads, but materialization must recompute whenever source data changes
  • Called "live tables" in some systems (e.g., Databricks)
Recommended Workflow

Temp tables while developing (inspect each step) → package into a CTE once logic is confirmed (clean single query) → promote to a view / materialized view if broadly useful across the org.

07 · Web APIs
APIs & JSON with Python Requests
▼

APIs return data in JSON: key-value pairs, nested dictionaries, and lists. The requests library handles the call and parsing: requests.get(url, params=dict) → response.json() gives you a Python dictionary.

StatusMeaning
200Success
404Resource not found
500Server error or permission denied

The Three APIs Used in Class

  • IP geolocation (ipapi.co): returns city, region, country, zip, lat/lon, ISP. No parameters needed — returns the location of the calling machine. Colab users get different locations depending on which data center they hit (Las Vegas, Singapore, Taiwan, Georgia…).
  • OpenWeatherMap: current weather + forecasts. Parameters: lat, lon, exclude, units, mode, appid — passed as a dictionary to requests.get, never manually concatenated into the URL. Nested response: current.temp, current.humidity, daily[], hourly[].
  • News API: headlines across ~150,000 outlets. Parameters: country, category, apiKey. Response: status, totalResults, articles (author, title, description, url, publishedAt). Paywalled outlets return metadata + URL only, not full content.
Chaining APIs — The Mash Pattern

Get lat/lon from the IP API → feed directly into the weather API call. The output of one API becomes the parameters of the next.

08 · LLM APIs
OpenAI API & Structured Outputs
▼

get_completion() Wrapper

  • Wraps the chat completions call; takes a system prompt (persona/behavior) and a user prompt
  • Temperature (0–2): low (~0.2) = focused, consistent, factual; high (~1.5) = varied, creative. Use high when generating multiple diverse summaries of the same content.
  • n parameter: request multiple completions in one call

Sentiment & Extraction Patterns

  • Basic sentiment: returns a verbose explanation
  • Constrained output: "respond with only 'positive' or 'negative'" → single word
  • Emotion extraction: returns a list (satisfaction, gratitude, frustration, disappointment…)

Structured JSON Output

  • Specify the schema in the prompt: "format your response as a JSON object with keys: item, brand, sentiment"
  • Add: "if information is not present, use null as the value"
  • The API can also enforce structure via the response_format parameter with a Pydantic model
  • Increasingly common pattern: unstructured text → structured data pipelines
Don't
Never hardcode API keys in notebooks or code files — they end up in version control.
Do
Store keys in a cloud secret manager (e.g., Google Cloud Secret Manager) and access them via the secret manager API at runtime.

09 · Hands-On Project
Citi Bike Pipeline → Streamlit Dashboard
▼
Goal

Full working dashboard by 5:30 visualizing how weather affects NYC Citi Bike trip volume — snow, rain, wind, temperature, humidity, fog, thunderstorms. Pre-built weather tables: nyu_dataset.weather and weather_daily_new_york_city.

Data Source

  • Citi Bike public archive (citibikenyc.com), ~300M trips, files organized by year then month
  • Schema changed partway through the archive's history; old and new formats overlap in a transition period — must deduplicate
  • JC (Jersey City) files are separate and smaller

Recommended Pipeline Architecture

  1. Copy raw zip files to a Google Cloud Storage bucket (do not process locally)
  2. Load raw files into BigQuery as raw tables
  3. Build a unified view reconciling old/new schemas and deduplicating the overlap period
  4. Aggregate to a daily summary table (trip counts by member type, etc.) — never query 300M rows per visualization
  5. Join daily trip summary with weather_daily on date
  6. Build a Streamlit dashboard on the joined table → deploy to Cloud Run

Development Tips (Prof's)

  • Use temp tables during development to inspect intermediate results
  • Validate row counts against a known aggregate from the source before moving on
  • Keep the laptop as a "dumb remote terminal" — all heavy processing in the cloud
  • Long Claude Code sessions pollute context and slow responses — start fresh sessions and merge pull requests to carry context forward
  • Claude Code saves session context into PR comments on GitHub — always merge PRs so the next session can recover prior context

Quick Reference
Things to Know Cold
▼
  • WHERE filters rows before aggregation; HAVING filters aggregates after. You cannot filter on an aggregate with WHERE.
  • Subquery in HAVING replaces hardcoded thresholds → portable, reusable queries (national-average pattern).
  • Semi-join = WHERE id IN (subquery) — filter via another table, return columns from one. Anti-join = NOT IN — excludes multi-genre rows entirely; null caveat: rows with no entry at all slip through.
  • Lift = segment_pct / other_segment_pct; > 1 means over-indexing. Always normalize by group size before comparing imbalanced segments (936 vs. 6,461).
  • Temp table → CTE → view/materialized view — the development-to-production promotion path.
  • Materialized views: scheduled vs. incremental (delta) refresh; BigQuery supports both, incremental not for all query types.
  • HTTP codes: 200 success · 404 not found · 500 server error/permission denied.
  • Pass API params as a dict to requests.get, never string-concatenate into the URL.
  • Temperature: low = consistent/factual, high = creative/diverse. Constrain LLM output format in the prompt or enforce with response_format + Pydantic.
  • Secrets live in a secret manager, never in code.
  • Pipeline shape: raw files → GCS bucket → BigQuery raw → unified view → daily aggregate → join weather → Streamlit on Cloud Run.
