01 · Motivation
What Is Big Data?
▼
Working Definition

"Big data" = data too large to fit on one machine, requiring a cluster of computers to store and process. This definition is always true — data growth consistently outpaces hardware capacity. No matter how powerful a single machine gets, datasets exist that exceed it.

Real-World Scale Examples

  • IoT sensors — industrial machines (GE, aircraft engines) collect vibration and fracture data second-by-second for predictive maintenance
  • Financial transactions — every Visa/Mastercard swipe hits servers in real time
  • Social media — every like, comment, and post timestamped and stored across billions of users

From Samples to Full Populations

Statistics evolved when data was scarce — sampling was a necessity, not a virtue. Now, tools exist to collect and analyze everything: attendance, clicks, EZ-Pass records, purchases. The value proposition of big data: companies can analyze all the data, not just a representative slice.

Transaction Databases vs. Analysis Environments

Don't
Never run analysis on a live transaction DB (Oracle, MySQL). These support customer-facing operations — heavy analytical queries slow them down and degrade customer service.
Do
Copy data into a separate analysis environment — a data warehouse, data lake, or Hadoop. Hadoop and similar tools are for analysis only, never for supporting live transactions.

02 · Core Concept
MapReduce & Hadoop
▼
The One-Liner

"MapReduce is the recipe, Hadoop is the dish." MapReduce is the algorithm — invented by Google researchers, who built the proprietary Google File System around it. Hadoop is the open-source implementation, built by researchers at Yahoo and others, available to everyone.

Core Idea — Distribute Storage AND Computation

  • Split a massive dataset into chunks; store chunks across a cluster
  • Instead of sending all data to one computer, send subtasks to each node
  • Each node processes its local chunk and returns partial results; the master aggregates them

Cluster Architecture

  • One master node coordinates all activity
  • N worker nodes store data and perform computation
  • Commodity hardware used intentionally — cheap, not high-end, failure-prone (and that's fine, see below)

Fault Tolerance Through Replication

  • Each data chunk replicated 3× by default (configurable to more)
  • Copies distributed randomly across different nodes
  • If any node fails, its chunks survive elsewhere — data is never lost
  • Nodes can be unplugged and replaced without disrupting the cluster
Prof's Analogy

Like the T-1000 in Terminator — pieces fall off, but it reassembles itself and keeps going.

Horizontal Scaling

Scaling is additive: just add more nodes as data grows; no need to replace existing hardware. Before Hadoop, the only option was buying a bigger single machine — an approach that hits a ceiling. Hadoop's horizontal scaling does not.

Disk-Based Processing

Hadoop uses disk (HDFS) for both storage and processing: read from hard drive into RAM → process → write back to disk. Suitable for very large datasets, but slower due to constant disk I/O. Analogy: like Prince of Persia loading one screen at a time from the hard drive.

03 · Key Distinction ★
Spark vs. Hadoop
▼
Hadoop (MapReduce)Spark
Where data livesDisk (HDFS) — read/write per stepDistributed RAM across all cluster nodes simultaneously
SpeedSlower — constant disk I/OMuch faster — no repeated disk reads/writes during computation
Best forStorage (HDFS) — "not going anywhere"Processing — replaces Hadoop MapReduce & Pig for transformation
CaveatWorks at any scaleNeed enough aggregate RAM across the cluster relative to your dataset
RAM Analogy

Spark = loading the entire Prince of Persia game into RAM at once vs. Hadoop loading one screen at a time from disk. If your cluster's combined RAM fits the dataset, Spark wins on speed.

  • Hadoop remains the standard for storage (HDFS); Spark replaces it for processing
  • Pig (Hadoop-era transformation tool) is being replaced by Spark for data transformation
  • Databricks is the company behind Spark — IPO long anticipated, not yet public
  • PySpark = the Python layer on top of Spark, making it accessible for Python-native data work — this is what we use in this course

04 · Tooling
The Hadoop Ecosystem
▼
ToolRoleKey facts
SqoopIngestPulls data from relational DBs (Oracle, MySQL, SQL Server) into HDFS. Bridges operational transaction DBs and the Hadoop analysis environment.
PigTransformCleans, joins, filters, recalculates. Named because "pigs eat anything" — ingests any data format. Uses temporary schema (no persistent tables, no clutter). Less popular now — Spark does it better.
HiveReportStructured queries & reports. Developed at Facebook (Yahoo contributed). Uses persistent schema — tables survive the session, stored on disk, so external BI tools (Tableau, Power BI) can connect. Use case: slice sales by region × demographics × product.
HDFSStoreThe distributed storage layer. Tracks what data is where, manages replication, handles node failures automatically.
YARNOrchestrate"Yet Another Resource Negotiator" — manages cluster resources in the background. Analysts never touch it directly.
Pig vs. Hive — Likely Quiz Material

Pig = temporary schema, appropriate for transformation (intermediate results shouldn't clutter the environment).
Hive = persistent schema, appropriate for reporting (tables must survive so BI tools can connect).

Outside This Course's Scope

  • Graph data (email networks, financial transaction networks, social graphs) → specialized graph databases
  • Streaming data (real-time stock feeds, fraud detection) → tools like Storm

Open Source Model

Hadoop and most ecosystem tools are free as in "free speech" (modifiable) and "free beer" (no cost). Consulting companies exist to install and manage Hadoop for enterprises. Large companies often run Hadoop on-premise; cloud providers offer managed versions (like Dataproc).

05 · Pipeline
Typical Big Data Workflow
▼

Full Pipeline — Raw Data to Insight

  1. Ingest — Sqoop pulls structured data from RDBMS (Oracle, MySQL) into HDFS
  2. Store — HDFS holds the data in distributed, replicated chunks as flat files (CSV/TXT)
  3. Transform — Pig (or Spark) cleans, joins, filters, and reshapes the data
  4. Report — Hive aggregates and structures data into persistent tables
  5. Visualize — connect Hive tables to Tableau or Power BI for charts and dashboards
  6. Analyze — apply machine learning and predictive modeling on the structured output

Why Raw Data Needs Reshaping

  • LinkedIn activity arrives as individual timestamped events — analysts bucket it by hour to find peak usage patterns
  • Raw Facebook/Instagram interactions need aggregation before any trend is visible

Batch vs. Streaming

  • Batch — process a stored dataset all at once (typical SQL/Hadoop workflow)
  • Streaming — process data in real time as it arrives (Visa fraud detection, live stock aggregation). Requires specialized tools; the Hadoop ecosystem is primarily batch-oriented.
No Updates in Hadoop

Hadoop is not designed for record updates — it's an analysis environment, not a transaction system. To "clean" data: transform it, save to a new file, delete the original. (Exceptions like Apache Iceberg allow updates, but they're the exception, not the rule.)

06 · Foundations
Linux & Open Source Foundations
▼
  • Hadoop runs on Linux only — all ecosystem tools (Pig, Hive, Sqoop, HDFS) run on Linux
  • Linux is free and open source: code is publicly available, modifiable, redistributable. Pull request model — anyone can propose a change; if the community accepts it, it ships globally. Contrast: Windows/macOS are closed source.
  • Unix (created at Bell Labs, NJ) predates Linux and is the conceptual ancestor of most modern OS design. The C language also came out of Bell Labs alongside Unix.
  • Linux "flavors" (distributions): Red Hat, Ubuntu, Debian — core commands are largely consistent across them

Google Cloud — Same Workflow, Managed Services

ServiceRole
Google StorageCheap long-term data storage; no analytics capability on its own
BigQuerySQL queries + visualizations on millions of rows (impossible in Excel). Data must be explicitly imported from Storage before querying.
DataprocGoogle's managed Spark/Hadoop cluster service

Dataproc Cluster Setup Walkthrough

  1. Standard config: 1 master + 2 workers — the minimum qualifying Hadoop cluster. (High-availability alternative: 3 masters + workers — more powerful, more expensive.)
  2. Enable Jupyter Notebook component under advanced configuration
  3. Enable cloud platform scope so the cluster can access Storage buckets
  4. Uncheck "internal IP only" — leaving it checked prevents external login to your own machine
  5. Link a staging bucket — code and outputs from Spark/Hadoop sessions save to Storage, not the cluster
  6. Delete the cluster immediately after use — data persists in the Storage bucket, so nothing is lost
Cost Logic — Why Storage and Dataproc Are Separate

Storage costs fractions of a cent per GB per month. Dataproc nodes cost ~$25/machine/month — a 10-node cluster is ~$250/month. So: keep data in Storage permanently, spin up Dataproc only when processing is needed, then delete it.

Common Cluster Creation Errors (Hit in Class)

IAM error
Compute service account lacks the "Dataproc Worker" role. Fix: copy the service account email from the error → IAM → grant "Dataproc Worker".
Region mismatch
Storage bucket and Dataproc cluster in different regions caused failures for some students. Switching the cluster region (e.g. to US East 1) resolved it in some cases.
UI bug
Cluster may show "provisioning" status with no error description — check the logs for the real detail.

Quick Reference
Things to Know Cold
▼
  • Big data definition: too large for one machine → needs a cluster. Always true because data growth outpaces hardware.
  • MapReduce vs. Hadoop: recipe vs. dish. Google invented the algorithm (+ Google File System); Hadoop is the open-source implementation (Yahoo et al.).
  • Replication = 3× by default, random distribution across nodes → fault tolerance on commodity hardware.
  • Hadoop = disk (slower, any scale) · Spark = distributed RAM (faster, needs enough aggregate RAM). Hadoop stays for storage; Spark wins processing.
  • Pig = temporary schema (transform) · Hive = persistent schema (report → BI tools). Sqoop ingests from RDBMS. YARN orchestrates in the background.
  • Pipeline order: Ingest (Sqoop) → Store (HDFS) → Transform (Pig/Spark) → Report (Hive) → Visualize (Tableau/Power BI) → Analyze (ML).
  • No record updates in Hadoop — transform → new file → delete original. Analysis environment ≠ transaction system.
  • Cost model: Storage ≈ pennies, cluster ≈ $25/node/month → data lives in Storage, clusters are ephemeral. Delete the cluster after use.
  • Dataproc gotchas: Dataproc Worker IAM role, region match between bucket and cluster, uncheck internal-IP-only, link a staging bucket.
