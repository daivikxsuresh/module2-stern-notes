A1 · Motivation
Why Databases? The Case Against Spreadsheets
▼
Real-World Story — The Greece Pension Disaster

In 1995, Greece computerized pension records. Convention: enter 999999999 as a placeholder for unknown amounts. When Greece converted to the Euro in 2001, those placeholders became real-looking €100M+ receivables per pension. By 2008, the system showed a 15.5% GDP annual deficit. Politicians promised to "collect billions from big debtors." Reality: over €3 billion in fake receivables — all from forgotten placeholder values in a flat database with no constraints and no single source of truth.

The root issue isn't a technology problem — it's a data architecture problem. Storing everything in one giant flat table (orders, customers, books all jammed together) creates three structural failure modes called data anomalies:

Insertion
Can't add information without inventing fake data. A new book can't be added to the catalog until someone places an order — books only exist as part of order rows. Gaps in required fields get filled with XXX, 99999, or NULL placeholders.
Deletion
Deleting one thing accidentally destroys unrelated information. Customer Lee Sproull only appears on Order #2. Delete that order → their name, ID, and address are permanently gone from the entire system.
Update
The same fact lives in multiple rows — update some, miss others → contradictions. Jeff Bezos's address appears on Orders #1, #6, and #8. Update one → three different addresses for the same person. Classic customer service nightmare: "We have your old address in billing, a different one in our main system."
🔧
A1 · Solution
Database Normalization
▼

Goal: one single authoritative source of truth for every piece of data. Instead of one giant flat table, split into distinct logical entities — Customers, Books, Orders — and link them together with keys. Each fact lives in exactly one place.

Insertion ✓
Add a new book to the Book table anytime — no fake order required. Books exist independently of orders.
Deletion ✓
Delete an order → customer record survives untouched in the Customer table.
Update ✓
Change Bezos's address in one place. Every order automatically reflects the new address — they all just point to the same Customer ID.
Startup Pattern

Many startups begin with MongoDB or a flat schema — fast, flexible, no upfront design. After 2–3 years of growth, they need analytics. They open the database and discover an unorganized mess. What follows is a year-long data cleanup migration. Design for normalization early, or pay for it later.

A2 · ERD Fundamentals
Entities, Attributes & Primary Keys
▼

Core Vocabulary

  • Entity — a thing we want to store information about (rectangle in ERD). Becomes a table in the final database. Examples: Students, Courses, Products.
  • Instance — one specific row. e.g. ("Daivik", "Suresh", 2001, "M")
  • Attribute — a property of an entity (oval in ERD). Each has a domain — the set of valid values.
  • Relationship — an association between entities, named with a verb (Student enrolls in Course).

Domain Restrictions — First Defense Against Bad Data

Domain constraints catch bad values at entry time, before they corrupt the database:

  • Year of birth: INTEGER BETWEEN 1940 AND 2010 — not 99, not 0.5
  • Gender: ENUM('M','F') — not free text like "male" / "men"

The Greece disaster could have been partially prevented with a domain constraint rejecting 999999999.

Primary Keys

The attribute(s) that uniquely identify each instance. Two hard rules:

  1. No two instances share the same PK value (uniqueness)
  2. Each instance has exactly one non-null PK value

Composite PK — uniqueness only holds when combining two attributes. Examples: (CourseID + SectionNumber), (BuildingAddress + ApartmentNumber), (AlbumID + TrackNumber).

🔑
A3 · Primary Key Design
Why Most Natural Keys Fail
▼
Golden Rule

Generate your own unique identifiers. Never use someone else's primary key. A key you didn't create can change, expire, get reassigned, or become non-unique in ways completely outside your control.

CandidateWhy it fails
SSNUniversities used SSN as student ID. International students got assigned fake SSNs. Later when they got real ones, the system had two records — course history split between them. Also: not everyone has an SSN.
Credit cardIdentifies an account, not a person. One person has multiple cards. Cards expire and get replaced with new numbers.
Passport numberExpires. People renew passports → same person, new key every 10 years.
EmailPeople change providers, forget old accounts → same person, multiple conflicting records.
Best Practice

Use an auto-generated surrogate key (StudentID, CustomerID, OrderID). Assign it once at record creation. Never expose it externally, never change it. This is what every major production system does.

A2 · Relationships
Relationships, Cardinality & Crow's Foot Notation
▼

Relationship Attributes

Some attributes belong to the connection itself, not to either entity alone. In a Student enrolls in Course relationship, Semester and Grade are relationship attributes — a grade isn't a property of the student (they have many grades from many courses) or the course (it has many students with different grades). It belongs to the specific enrollment event.

Three Relationship Types

  • One-to-one (1:1) — each office has at most one faculty advisor, each advisor has at most one office
  • One-to-many (1:N) — one advisor has many students, each student has exactly one advisor
  • Many-to-many (M:N) — students take many courses, each course has many students

Crow's Foot Notation (ERDPlus)

Each end of a relationship line carries two symbols:

  • Inner symbol = minimum (participation): pipe | = mandatory (min 1) · circle ○ = optional (min 0)
  • Outer symbol = maximum: pipe | = one · crow's foot ⟨ = many
SymbolsReadingExample
| |Exactly one, mandatoryA dept must have exactly one building address
| ⟨One or more, mandatoryA department must have ≥1 employee
○ ⟨Zero or more, optionalA course may have 0 to many enrolled students
○ |Zero or one, optionalA student may or may not have an advisor on record
Design Balance

Too rigid = blocks legitimate edge cases, forces workarounds. Too flexible = "anything goes" → data chaos and eventual Greece-style disasters. Find the constraints that reflect real business rules, then enforce them at the DB level — not in application code.

A3 · Core Algorithm ★ Exam
ERD → Relational Schema Translation
▼

This is a mechanical, step-by-step algorithm. ERDPlus can auto-generate it from a completed ERD. Know every step cold for the exam.

  1. Check completeness — every entity has attributes + a PK; every relationship has cardinalities on both ends. Do this before proceeding.
  2. Entities → tables — one table per entity. Attributes become columns. PK stays PK.
  3. 1:N → FK on the "many" side — add a foreign key column to the "many" table pointing to the PK of the "one" table. If participation is mandatory (inner symbol = pipe, min = 1), set NOT NULL.
  4. 1:1 → FK on either side — add FK to one table + UNIQUE constraint to enforce max cardinality of 1.
  5. M:N → bridge table — create a new junction table. Its PK is the composite of both entities' PKs. Relationship attributes live here.
Constraint Mnemonic

NOT NULL = mandatory participation (min = 1, inner pipe symbol).
UNIQUE = max cardinality = 1 (enforces the "one" side of a 1:1 relationship).

A3–A4 · M:N Relationships
Bridge Tables — "Bread and Butter of Most Systems"
▼

Every M:N relationship requires a bridge table (junction / associative table). You can't add a FK to either entity's table — that would require storing a list of values in one cell, which violates first normal form entirely.

Painter / Owner Example

TableColumnsNote
PainterPainterID, Name, DOBStandard entity
PaintingPaintingID, Name, PainterID FK, GalleryID FK1:N from Painter
OwnerPersonID, Name, AddressStandard entity
Buys (bridge)TransactionID, PurchaseDate, Amount, OwnerID FK, PaintingID FKM:N bridge

Employee / Department / Job (from class)

TableColumnsWhy
DepartmentDeptNum, DeptNameStandard entity
EmployeeID, Name, DeptNum FK1:N → FK on many side
JobJobNum, JobNameStandard entity
JobAssignment (bridge)EmpID FK + JobNum FK (composite PK), HoursM:N bridge; Hours is a relationship attr
Key Insight — Derived vs. Stored Attributes

Never store "Number of Employees" per department. Compute it with COUNT(*). Storing it reintroduces update anomalies — you'd have to update it every hire and departure.

Hours Worked on a job = a relationship attribute. It belongs in the bridge table (JobAssignment), not in Employee or Job — because it's a property of that specific assignment pairing, not of either entity alone.

A5 · SQL DDL
Creating Tables — Key DDL Constraints
▼

ERDPlus generates CREATE TABLE SQL from the relational schema. Know what each constraint does:

ConstraintWhat it enforces
PRIMARY KEY(col)Unique identifier — no duplicate values, no nulls
NOT NULLMandatory participation — inner symbol = pipe (min = 1)
UNIQUEMax cardinality = 1 — enforces the "exactly one" side of a 1:1
FOREIGN KEY(col) REFERENCES T(pk)DB rejects rows pointing to non-existent PKs — second defense after domain constraints

Add entities + attributes + PKs → add relationships + cardinalities on both ends → Main Menu → Convert to Relational Schema → verify → Convert to SQL → fine-tune data types. Use erdplus-old.com (the old version used in class).

Quick Reference
Things to Know Cold
▼
  • Name and define the 3 anomalies with an example each: insertion → fake data required · deletion → destroys unrelated info · update → same fact in multiple rows → contradictions.
  • Read a Crow's Foot diagram and state min/max on both sides in plain English. Inner symbol = min, outer = max.
  • ERD → relational schema rules: 1:N → FK on the "many" side; M:N → bridge table with composite key; 1:1 → FK on either side + UNIQUE.
  • Derived vs. stored attributes: never store what you can compute (NumEmployees). Relationship attributes (Hours, Grade, Semester) live in the bridge/join table.
  • PK candidates to reject: SSN, phone, email, passport — know the specific reason each fails.
  • NOT NULL = mandatory participation (min = 1). UNIQUE = max cardinality = 1. Know both.
  • The Greece story = the motivating example for all of normalization. Know the arc: placeholder data → currency conversion → fake receivables → political fallout.
