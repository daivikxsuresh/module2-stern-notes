Module 1 — ER Model & Relational Schemas (slides A1–A5)
A1 · Motivation
Why Databases? The Case Against Spreadsheets

The Greece story (the best example): In 1995, the Greek government computerized pension records. Convention: enter 999999999 as a placeholder for unknown pension amounts. When Greece converted to the Euro in 2001, those fake numbers became real-looking €100M+ receivables per pension. By 2008, the system showed a 15.5% GDP annual deficit — governments fell, politicians promised to "collect billions from big debtors." Reality: over €3 billion in fake receivables from old data entry placeholders. Root cause: accumulated fake/placeholder data completely disconnected from its original context.

The problem: Storing everything in one giant flat table — orders, customers, books all mixed together — creates a minefield of errors. Three fundamental anomalies:

Insertion
Can't add info without inventing fake data. Can't add a new book to the catalog until someone orders it — a book only exists as part of an order row. You end up filling required fields with XXX, 999999, placeholder values.
Deletion
Deleting one thing accidentally destroys another. Customer Lee Sproull only appears on Order #2. Delete that order → their name, ID, address are gone forever from the entire database.
Update
Same fact lives in multiple rows — update some, miss others → contradictions. Jeff Bezos's address appears on Orders #1, #6, #8. Update one → now three different addresses for the same person. Classic customer service nightmare: "We have your old address in billing, different from the main system."
A1 · Solution
Database Normalization

Goal: one single authoritative source of truth for every piece of data. Stop storing one giant list. Split into distinct logical entities — Customers, Books, Orders — and link them with keys.

How normalization solves each anomaly:

Insertion ✓
Add a new book to the Book table anytime — no fake order needed. Books exist independently.
Deletion ✓
Delete an order → customer record survives in the Customer table, completely untouched.
Update ✓
Change Bezos's address in ONE place (his Customer row). Every order automatically reflects it — they all point to the same Customer ID.
A2 · ERD Fundamentals
Entities, Attributes & Primary Keys

Entity = a thing we want to store information about (drawn as a rectangle). Examples: Students, Courses, Products. Each entity becomes a table in the final database. An instance is one row — e.g. ("Daivik", "Suresh", 2001, "M").

Attribute = a property of an entity (drawn as an oval). Each attribute has a domain — the set of valid values. Domain restrictions are your first defense against bad data:

  • Year of birth: integer between 1940–2010 (not 99, not 0.5)
  • Gender: restricted set ENUM('M','F') — not free text like "male"/"men"

Primary Key (PK) = the attribute that uniquely identifies each instance. Two rules:

  1. 1No two instances share the same PK value (uniqueness)
  2. 2Each instance has exactly one PK value (not null, not multiple)

Composite PK: sometimes uniqueness only holds when combining two attributes together. Examples: (CourseID + SectionNumber), (BuildingAddress + ApartmentNumber), (AlbumID + TrackNumber).

A3 · Primary Key Design
Choosing a Good PK — and Why Most Natural Keys Fail

Rule: generate your own unique identifiers. Don't use someone else's primary key.

Common candidates and their fatal flaws:

CandidateWhy it fails
SSNNot everyone has one → fake SSNs for international students. Real disaster: universities used SSN as student ID. International students got fake SSNs, later got real ones — now two records, courses split between them.
Credit cardIdentifies an account, not a person. One person has multiple cards.
Passport numberExpires. People get new ones over a lifetime → same person, different key.
Email addressPeople change emails, forget old accounts → same person, multiple records.
Best practice: auto-generate a surrogate key (StudentID, CustomerID, etc.) — stable, internal, never exposed to external systems. Assign it once and never change it.
A2 · Relationships
Relationships, Cardinality & Crow's Foot Notation

Relationship = an association between entities, named with a verb. Example: Student enrolls in Course.

Relationship attributes = properties that belong to the connection itself, not to either entity alone. Example: the "Enrolls" relationship carries Semester and Grade — not a property of Student (takes many courses) or Course (has many students).

Cardinality = how many instances can participate on each side. Two dimensions: minimum (participation) and maximum (key constraint).

Three relationship types:

  • One-to-one (1:1) — each office max one advisor, each advisor max one office
  • One-to-many (1:N) — one advisor has many students, each student has one advisor
  • Many-to-many (M:N) — students take many courses, each course has many students

Crow's Foot Notation — used in ERDPlus. Two symbols on each end of the line:

  • Inner symbol = minimum — pipe | = mandatory (min 1); circle ○ = optional (min 0)
  • Outer symbol = maximum — pipe | = one; crow's foot ⟨ = many
Symbol comboReadingExample
||Exactly one, mandatoryA professor must have exactly one office
|⟨One or more, mandatoryA department must have ≥1 instructor
○⟨Zero or more, optionalA course may have 0 to many students enrolled
○|Zero or one, optionalA student may have 0 or 1 university email
Design balance: too rigid = blocks legitimate edge cases. Too flexible = "anything goes" → data chaos. Common startup pattern: MongoDB first (fast, flexible), then migrate to structured DB after 2–3 years when analytics becomes critical. Timeline: success → need analytics → discover data is an unorganized mess → year-long cleanup project.
A3 · Core Algorithm ⭐
ERD → Relational Schema Translation

This is a mechanical, step-by-step process. ERDPlus can auto-generate it once the ERD is complete.

  1. 0Check completeness — every entity has attributes + PK; every relationship has cardinalities on both sides.
  2. 1Entities → tables — one table per entity. Attributes become columns. PK stays PK.
  3. 2One-to-many → FK on the "many" side — add a foreign key column to the "many" table pointing to the PK of the "one" table. If participation is mandatory (min=1), make FK NOT NULL.
  4. 3One-to-one → FK on either side (or merge both tables). Add UNIQUE to enforce max cardinality of 1.
  5. 4Many-to-many → bridge table — create a new junction table. Its PK is usually the composite of both entities' PKs. Relationship attributes live here.
Mnemonic for constraints: NOT NULL = mandatory participation (min = 1). UNIQUE = max cardinality of 1 (enforces 1:1). Remember this for the final exam.
A3–A4 · M:N relationships
Bridge Tables — "Bread and Butter of Most Database Systems"

Every many-to-many relationship requires a bridge table (also called junction table, associative table). You cannot put a FK on either side — it would require storing a list of values in one cell, which breaks normalization.

Painter example: Painting can be owned by many people, Person can own many paintings.

TableColumns
PainterPainterID, Name, DOB
PaintingPaintingID, Name, PainterID FK, GalleryID FK
OwnerPersonID, Name, Address
Buys (bridge)TransactionID, PurchaseDate, Amount, OwnerID FK, PaintingID FK

Employee/Department/Job example: Employee works in one Department (1:N → FK in Employee table). Employee does many Jobs, Job has many Employees (M:N → bridge table).

TableColumns
DepartmentDeptNum, DeptName
EmployeeID, Name, DeptNum FK
JobJobNum, JobName
JobAssignment (bridge)EmpID FK + JobNum FK = composite PK, Hours

Key insight on "derived" data: Number of Employees per department — do NOT store this. It can always be computed with COUNT(). Storing it reintroduces update anomalies. Hours Worked on a job = a relationship attribute → goes in the bridge table, not in Employee or Job.

A5 · SQL DDL
Creating Tables — Basic DDL Syntax

Once the relational schema is finalized, ERDPlus can auto-generate the CREATE TABLE SQL. Know the key clauses:

ConstraintWhat it enforces
PRIMARY KEY(col)Unique identifier — no duplicates, no nulls
NOT NULLMandatory participation — min cardinality = 1
UNIQUEMax cardinality = 1 (enforces 1:1 relationships)
FOREIGN KEY(col) REFERENCES Table(pk)DB rejects rows pointing to non-existent PKs — second defense against bad data

ERDPlus workflow: Add all entities + attributes + PKs → add all relationships + cardinalities → Main Menu → Convert to Relational Schema → check everything looks right → Convert to SQL → fine-tune data types. Use erdplus-old.com (the old version is what's used in class).

Know the difference between a stored attribute (num employees) vs a derived attribute (COUNT) — never store what you can compute. And where relationship attributes live (in the bridge table, not in either entity).
